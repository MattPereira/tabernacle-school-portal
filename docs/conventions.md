# Codebase conventions

The living map of where things go and the rules to follow. Frozen rationale for every choice here lives in [ADR-0002](adr/0002-codebase-conventions.md); if this file and the ADR ever disagree, the ADR is the record of *why* and this file is the record of *what now*.

## Layout

```
src/                      everything the running app imports at runtime
├── app/                    Next.js plumbing — routes, server actions, RSC, better-auth wiring.
│                           NO business logic; calls into lib/.
├── lib/                    the app's non-UI, non-route code
│   ├── db/                   schema/ (auth.ts + facts.ts + portal.ts) + client.ts   [wiring]
│   ├── auth/                 better-auth instance + getViewer()              [wiring]
│   ├── facts/                rate-limited read-only FACTS API client          [wiring]
│   ├── sync/                 read-only FACTS → DB sync + status reads    [rule module]
│   └── identity/             resolveAccess(email, deps): FACTS-derived gate [rule module]
└── components/             presentational — the only place JSX-with-styling lives
    ├── ui/                   shadcn/ui primitives. Generated by the CLI, ours to
    │                         edit but not to hand-write from scratch.
    └── *.tsx                 shared surface: portal-shell, app-sidebar, theme-provider,
                              theme-toggle, sign-in/out buttons

postcss.config.mjs        Tailwind v4's one build hook
components.json           shadcn CLI config — style, base colour, path aliases
src/app/globals.css       Tailwind import + the semantic-token variables (`:root` / `.dark`)

tests/                    Vitest suites — not runtime-imported, so outside src/
├── identity/                one file per behavior at the resolveAccess seam
├── sync/                    one file per behavior at the sync(deps) seam
└── support/                 db.ts — PGlite + migrations; facts.ts — the fake FACTS client

reference/                external-system REFERENCE material (read while building; not imported)
└── facts/                   api-definitions.json — the FACTS API Swagger spec

scripts/                  ops-time scripts, run once — not runtime-imported
├── build-identity-links.mjs  reviewed Workspace → FACTS matcher prototype
├── facts/                    FACTS fetchers + shared rate-limited client
├── google/                   ops-time Workspace prototypes; never runtime dependencies
└── data/                     shared I/O for all of the above [gitignored — student PII]

secrets/                  gitignored service-account keys (Google domain-wide delegation)

drizzle.config.ts         points at src/lib/db/schema
docs/                     CONTEXT.md glossary, adr/ decision records, this file
```

## The rules

1. **The `src/` barrier is "does the running app import it?"** — not "is it Next.js?". Framework-free logic still ships, so it's in `src/`. Migrations, seed scripts, data, and external reference do not ship → root.
2. **`app/` holds no business logic.** Routes/actions/RSC call into `lib/`. If there's an `if` deciding a school rule inside `app/`, it's misfiled.
   Auth mutations follow the same form → server action pattern as other mutations; their actions are thin better-auth wiring.
3. **Rule modules accept deps, return results, and never import `next/*`.** `lib/sync` and `lib/identity` take their db handle / FACTS client as arguments so they test without booting Next. Grep a rule module for `next` → should be zero hits. Identity derives from FACTS snapshot data inside `lib/identity`; routes only act on its result.
4. **Schema splits by ownership.** `db/schema/facts.ts` = local, read-only, potentially stale FACTS snapshots; `db/schema/portal.ts` = portal-owned operational state (`sync_run`); `db/schema/auth.ts` = better-auth's own tables, shaped by its adapter and not ours to tune. The `facts_*` names communicate source; comments and [ADR-0005](adr/0005-facts-derived-identity.md) carry snapshot semantics. The portal owns no identity or role state.
5. **External API contracts live in `reference/`, not `docs/` and not `src/`.** Material you read while building (not imported code); the runtime client lives in `src/lib/`.

## UI

- **UI components live in `src/components/`; `app/` composes them.** A route file's job is to fetch, branch on the answer, and arrange components — not to carry the markup for a table or a form. `components/ui/` contains shadcn's generated primitives; the loose files beside it are ours. Reach for a shadcn primitive before writing a bespoke one, and pull it with the CLI (`pnpm dlx shadcn@latest add …`) rather than hand-writing it. This is rule 2 applied to presentation: `app/` still decides nothing.
- **Semantic tokens only — no raw colours.** Every colour comes from a shadcn/Tailwind semantic token: `bg-background`, `text-foreground`, `text-muted-foreground`, `border`, `bg-card`, `bg-muted`, `bg-destructive`, `text-primary`, … Never `bg-white`, `text-gray-900`, `text-red-500`, or a hex/`oklch()` literal in a component. Two things depend on it: dark mode is then correct by construction (the `.dark` block in `globals.css` re-points the same variables), and school branding later becomes a handful of variable edits instead of a sweep of every component. If a shade you need has no token, add a CSS variable in `globals.css` with a `.dark` counterpart — do not inline the colour.
- **Dark mode is `next-themes`**, `attribute="class"` + `defaultTheme="system"`, wired once in `app/layout.tsx` via `components/theme-provider.tsx`. Any new surface must be checked in both themes; the token rule is what makes that cheap, not a second pass of overrides.
- **Branding is deliberately unstyled.** The stock shadcn neutral palette ships until there is a ticket for Tabernacle's colours, logo, and type. Don't invent a palette.
- **Portal/auth boundary:** `(portal)/layout.tsx` is the staff-access gate and composes the shared `portal-shell`. Login and holding-page routes stay outside it, so they keep their focused auth-page presentation. Portal pages render only their page content; sidebar navigation, top header, viewer controls, and outer content width belong in `portal-shell`/`app-sidebar`.

## Testing

- **Vitest**, all tests under `tests/` (settled while building #18 — tests aren't runtime-imported, so the `src/` barrier keeps them out). Follow the module path: `tests/identity/` covers `src/lib/identity`.
- **Test the deep modules through their interfaces** — `sync(deps)`, `resolveAccess(email, deps)`. `app/` and components get little-to-no test; a presentation-only change ships without one (see #24).
- **Wiring gets no test, so behavior doesn't live in wiring.** If a requirement needs asserting and it sits in `lib/auth` or `app/`, that's the signal to move the decision into a rule module and inject what it needs (this is why `recordLoginAttempt` takes a `log`). Don't widen the no-test rule to cover logic — move the logic.
- **PGlite** for a real in-process Postgres — exercises real SQL/transactions, no Docker. `tests/support/db.ts` applies the real `drizzle/` migrations, so a migration that would fail in production fails in tests first.
- **No E2E / Playwright** unless a concrete flow later proves un-coverable more cheaply.
- Every ticket ships with a test.
